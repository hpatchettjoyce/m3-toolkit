# Project Notes: Monumentum Cast Recruiter & Tabletop Simulator Toolkit

This document serves as the primary system reference and onboarding manual for the **Monumentum Cast Recruiter** (M3 Toolkit) ecosystem. It provides human developers and automated agents with complete context on system components, internal data architectures, cross-platform communication, and standard workflows.

---

## 📌 System Architecture & Data Flow

The M3 Toolkit bridges three independent runtime environments—a **Google Sheets Database**, a **Browser-Based Visual Deck Builder (Google Apps Script Web App)**, and **Tabletop Simulator (TTS)**—to enable seamless deck recruiting, physical prototyping, and match play analytics tracking.

```text
       [ Google Sheets Database ]
          (Tab: IN Cast — all 200 cards)
                    │
                    ▼ (Export one CSV: "M3_TTS_DB - Cast.csv")
      [ Python Metadata Compiler ] ──(Generates CardImages.gs)──► [ Web App (GAS Backend) ]
         (generate_card_images.py)                                     │ (Serves Card Data)
                    │                                                  ▼
                    │ (Injects names/IDs, positionally)  [ Visual Cast Recruiter SPA ]
                    ▼                                            (CastRecruiter.html)
      [ Saved Object JSON Deck ]                                       │
       ("MonuMentuM DD-MM-YYYY.json" —                                 │
        one 200-card 'Cast' deck)                                      │ (Exports JSON Roster)
         (Loaded into TTS Chest)                                       │
                    │                                                  ▼
                    │                                        [ Player Clipboard ]
                    │                                                  │ (Pastes JSON to Pad)
                    ▼                                                  ▼
     [ Tabletop Simulator Gameplay ] ◄─────────────────────── [ TTS Loader Pad ]
       - Spawns Standees on Board                               (TTS_Loader.lua)
       - Deals Cards to Player Hand                                    │
       - Auto-Deploys Map Tiles (Font/Path)                            │ (Retrieves Match Data)
                    │                                                  ▼
                    └─────────────────────────► [ End Game Controller ]
                                                  (End_Game_Controller.lua)
                                                       │
                                                       │ (POSTs Winner & Rosters)
                                                       ▼
                                             [ Web App Webhook ]
                                              (Sheet tab: IN TTS)
```

**Off to one side of that flow** sit the checks and the asset pipeline, which nothing in the diagram
calls but every change has to pass: `validate_cast.py` (the one thing that runs offline — CSV shape,
row order, champion links, icon tokens, deck pairing), `build_svg_sprite.py` (embeds the inline icons
into the HTML, because Apps Script hosts no static assets), `make_contact_sheet.py` (the only check
that catches `DEX Cast` drifting out of step with `IN Cast`), and `check_theme_contrast.py` (colour
tokens). `UPDATING.md` says which to run when.

## 🏛️ Component Specifications

### 1. Web App & Webhook Backend (`webapp/`)

The web app is deployed as a single-page visual recruiter and automated webhook endpoint using Google Apps Script (GAS).

*   **Database Fetching (`getCardDatabase`)**:
    *   Retrieves raw card data from a **single** spreadsheet tab — **`IN Cast`**, all 200 cards (Champion, Familiar, Minion, Talisman, Special Action). The old `IN Cha-Tal` / `IN SP` pair is gone. The tab name is the `CAST_SHEET_NAME` constant at the top of `main.gs`; `getSheetByName()` matches exactly, so a rename means editing that one constant, `clasp push`, redeploy.
    *   Classes are stored in all caps in the sheet and normalised to Title Case at the parse boundary. `normaliseName()` here is the twin of `normalise_name()` in `validate_cast.py` — change both or neither.
    *   **🚨 `MATCH_SHEET_NAME` is not a second cast source.** It is the *write* destination for the TTS webhook (`IN TTS`); pointing it at a card-data tab appends match logs onto the bottom of the cards.
    *   **🚨 Global Namespace Caution**: In Google Apps Script, all `.gs` files share a flat global scope, so two files defining the same function name silently override one another. This previously happened here — `CardDatabase.gs` shipped a competing `getCardDatabase()`. That file has since been deleted (its `getRawCardDatabase()` helper was never called by anything), leaving the structured category-mapping implementation in `main.gs` as the sole definition. Do not add a second card-fetching implementation in another `.gs` file.
*   **Webhook Ingestion (`doPost`)**:
    *   Serialises match-log writes behind a script lock (`LockService.getScriptLock()`, 30-second `waitLock`) so two simultaneous End Game submissions can't interleave `appendRow` calls.
    *   The `finally` block releases the lock only if `waitLock()` actually returned (tracked by a `hasLock` flag). Releasing unconditionally would have meant calling `releaseLock()` on the one path where the lock was never held — the timeout path.
*   **Visual Recruiter SPA (`CastRecruiter.html`)**:
    *   Provides players with a responsive interface to select a Dominion faction, review card text/stats, and recruit a legal deck under compliance rules. Since Chunk 8 the shell is a two-column grid: `.container` (max `1600px`) beside a laid-out `.status-rail` (trackers, Print, Export) that folds into a sticky row above the builder below 1100px. **Card column counts are `@container` queries on `.container`, not viewport media queries** — the rail eats viewport width, so the viewport is the wrong thing to measure; only the phone step (<600px, one card per row) is a media query. As-built table: `UPGRADE_PLAN.md` Chunk 8 item 1.
    *   **Inline SVG icons in rules text**: rules and Keywords cells carry icon tokens (`{Icon:{M3/Icons/Prowess/Prowess Plus 1.svg}}`, or bare for dice) that `formatRulesText(text, { icons: true })` resolves to `<use>` references into a sprite `build_svg_sprite.py` writes between the `SPRITE_START`/`SPRITE_END` markers. Only the icons the CSV actually references are embedded; anything unembedded — and everything on paper — falls back to `[PROWESS +1]`-style text.
    *   **Sanitised Rules Text**: Card text from the spreadsheet is passed through `escapeHtml()` *before* `formatRulesText()` applies its bold/italic/icon markup, so only the markup the app generates is live HTML. Anything angle-bracketed in the sheet renders as literal text. The print-card stat line escapes its interpolated values the same way. If you add markup rules to `formatRulesText()`, keep them after the escape step.
    *   **Signature Action Segregation**: Splitting the Specials rendering into separate visual DOM grids (`#signature-container` vs `#specials-container`) to isolate a Champion's free Signature Actions from generic, cost-allocated Special Actions.
    *   **JSON Roster Sharing**: 
        *   *Export*: Outputs a structured, backward-compatible JSON string containing recruited card IDs, attached talismans, and general specials.
        *   *Import*: Offers a top-aligned, modal-driven importer. Paste in a shared JSON string, and it recursively resolves selections using Modern Unique IDs, falling back to name-based lookups if needed, and automatically repopulates the active builder grid.
*   **Low-Ink Printer-Friendly Cards**:
    *   **Butt-Joined 3x3 Centered A4 Pages**: Generates print pages grouped strictly into blocks of 9. Each group is framed inside a precise A4 page container (`210mm x 297mm`) with a CSS margin (`left/right: 9.75mm`, `top/bottom: 15.15mm`) and a zero-gap grid. This ensures perfect page breaks, prevents edge clipping on home printers, and allows a single paper-cutter slice to separate cards.
    *   **Poker Sizing**: Cards are sized strictly to standard playing card sleeve dimensions: `2.5 inches x 3.5 inches` (63.5mm x 88.9mm).
    *   **Minimalist Dominion Borders**: Employs colored borders to distinguish factions without consuming excessive ink (Rhavlika: Red, Iro-Si-Khar: Blue, Voisira: Gold, Xalakith: Purple, Ahèserec: Green, Veritian: Teal).
    *   **Clean Drawing Canvases**: Displays a fixed `1.8in x 1.3in` empty artwork rectangle with a `2px` black border, enabling playtesters to sketch custom illustrations directly on physical prints.
    *   **Reference Copy Limits**: Limits character card printouts to exactly 1 reference card per unique recruited character (Champions, Loyals, Basics, Talismans, and Specials), suppressing duplicate sheets to maximize paper efficiency.
    *   **Auto-Minion Injection**: If a selected Dominion features native mid-game minions (**Iro-Si-Khar**'s *Driplet* or **Ahèserec**'s *Huskling*), the print system automatically appends a single reference card for that minion, even if the player did not explicitly recruit it in their list.

### 2. Python-Based Compiler Script (`dextrous/`)

The compilation script `generate_card_images.py` acts as the bridge between the raw sheet export (one CSV) and Tabletop Simulator's Saved Object file. **One CSV in, one deck JSON in; an ID-keyed `webapp/CardImages.gs` out and the deck JSON injected in place.**

*   **CSV Parsing & Coordinate Generation**:
    *   Scans the single exported cast sheet — `M3_TTS_DB - Cast.csv` at the repo root (`--csv` overrides; the export carries a BOM, so it is read as `utf-8-sig`).
    *   Computes and compiles sprite coordinates, auto-generating the `webapp/CardImages.gs` data structure, keyed by **card ID** (`01RHA-01CHP-0001`), not a positional `champ_0`.
    *   The deck defaults to the **newest** `dextrous/MonuMentuM DD-MM-YYYY.json` via `find_deck()` — `validate_cast.py` and `make_contact_sheet.py` share that resolution, so none of the three is pinned to a dated filename any more.
*   **🚨 The pairing is positional, and that is the whole risk**: deck card N takes its identity from CSV row N. A Dextrous export arrives with `Nickname`, `GMNotes` and `Description` all blank, so nothing in the file can be cross-checked against the CSV — if the two orders drift, every affected card is silently labelled with a different card's name. The script fails loudly on a length mismatch; `make_contact_sheet.py` (art next to injected name) is the only check that catches a same-length reorder. `IN Cast`'s row order is canonical and `validate_cast.py` enforces it, so **`DEX Cast` must mirror `IN Cast` row for row** — the rows cannot be reordered to fix anything.
*   **Unique ID Generation & Metadata Injection**:
    *   Constructs deterministic Unique IDs starting with a `SYN-` prefix for any spreadsheet items missing static IDs, and reports the count at the end of a run.
    *   Modifies the TTS Saved Object JSON deck in place:
        1.  Injects the clean, human-readable card name into the **`Nickname`** property (visible when players hover over cards in-game).
        2.  Injects the Unique ID string into the **`GMNotes`** property (invisible to players, but readable by Tabletop Simulator scripts).
        3.  Injects the card's rules text into **`Description`**.
    *   This dual-property structure allows players to see familiar names while scripts execute safe, unique ID-based actions.

### 2b. Offline Validator (`dextrous/validate_cast.py`)

Nothing in this repo can be unit-tested locally — Apps Script needs a deploy and TTS needs the game running — so this is the one thing that runs offline, and every chunk of the upgrade plan leans on it before asking for a manual test. It checks the CSV against `EXPECTED_HEADER`, the canonical row order (each row's `#` and its ID's trailing sequence must equal its row position), the class census, champion links (including the Dextrous-safe transliterations), the deck pairing, and the icon tokens — asset exists, embedded in the sprite, no stray braces. **It fails with "isn't in the web app yet" until `build_svg_sprite.py` has been re-run after a re-export that uses a new icon.**

### 3. Tabletop Simulator Automation Suite (`tts/`)

Tabletop Simulator scripts automate setup, layout physics, board deployment, and match recording.

*   **TTS Loader Pad (`TTS_Loader.lua`)**:
    *   **Workspace Auto-Clearing**: Clicking "Load" triggers `clearPlayerWorkspace()`, deleting all active cards in the player's Hand and all spawned models/standees in their Scripting Zone before loading a new roster to ensure clean transitions.
    *   **ID-Based Lookups**: Reads the pasted roster JSON and matches Unique IDs against the `GMNotes` properties of cards contained in the reference decks.
    *   **Collision-Free Teleportation Return Physics**: Pulls the matching card out of the deck, clones it, and uses a non-blocking instant teleportation command (`cardObj.setPosition(deck.getPosition())`) right before pushing the original back in (`deck.putObject(cardObj)`). This ensures 100% absorption and zero duplicate spills on the table.
    *   **Unified Hand Dealing**: To bypass Tabletop Simulator layout-zone physics engine bugs (where cards spawned directly onto zones merge into a deck before the zone aligns them), the Champion card, reference units, and Specials are dealt directly to the player's hand.
    *   **Calibrated Grid Model Spawning**: Spawns 3D model/standee figures directly on the table, matching the exact quantity from the JSON. It places the Champion standee first (as row 1 of the player's grid) and lines up recruited units on back rows (rows 2, 3, etc.). Characters spawn rotated `90` degrees around the Y-axis to face the players directly.
    *   **Auto-Summon Minion Pools**: If loading an **Iro-Si-Khar** or **Ahèserec** roster, the loader automatically draws the minion card (*Driplet* or *Huskling*) to the player's hand and clones/stacks exactly **12 standee copies** of that minion vertically on a final dedicated board row as a spawning pool.
    *   **Native Onboarding Scenario Controller**:
        *   Renders an elegant screen-space XML panel aligned to the center of the player's monitor with slide transitions.
        *   Routes XML dropdown selection events and clicks back to the script using dynamic GUID-based formatting (`self.getGUID()`).
        *   *Scenario Map Auto-Deployment*: When the Red Player loads a scenario, the script automatically deploys path and font tiles matching the map level (Scenarios 1 & 2: 2x2 grid, 1 font; Scenario 3: 4x4 grid, 3 fonts; Scenario 4/Standard Game: 6x6 grid, standard layout) asynchronously and in parallel with card loading.
        *   *Scenario Scaling*: Scenarios 1 & 2 represent reduced training games; the loader automatically suppresses spawning champions, minion standees, or drawing minion cards, only introducing them starting at Scenario 3.
*   **End Game Controller (`End_Game_Controller.lua` & Webhook)**:
    *   **Tactile 3D Button**: Replaced a complex column of buttons with a single central, static green **"End Game"** button attached to a dedicated token.
    *   **Holographic XML Pop-up Panel**: Clicking "End Game" triggers a floating XML UI menu hovering above the token, restricted to the Host, offering options: **Red Won**, **Blue Won**, **Draw**, or **Cancel**.
    *   **Global Match API**: The Cast Loader Pad caches successfully loaded rosters and logs Special Action plays. It exposes this data through a secure global API function: `getMatchDataJson()`. The End Game Controller queries this API via TTS's inter-script `call()` system, completely bypassing cross-script table ownership restrictions ("Attempt to perform operations with resources owned by different scripts").
    *   **Raw JSON Submission**: Standardized on Tabletop Simulator's positional `WebRequest.custom()` method with explicit `Content-Type: application/json` headers. This transmits a raw JSON body payload matching keys for both `loadedCasts` and `casts`. This guarantees Google Apps Script's `doPost(e)` receives and parses the payload cleanly, automatically populating columns in the **`IN TTS`** sheet tab.
*   **Model ID Injector Utility (`Model_ID_Injector.lua`)**:
    *   A table tool placed next to a reference Characters deck and a bag of raw 3D models.
    *   **Casing & Cost Cleanups**: Automatically strips parenthesized trailing costs from model names during database matching (e.g., `Obduron (6)` -> `Obduron`) and permanently clears prowess/fortitude description stats.
    *   **ID Assignment**: Copies the card's Unique ID from its `GM_Notes` and assigns it to the model's `GM_Notes`.
    *   **Script Injection**: Embeds the `Floating_Health_Tracker.lua` code into the model's script properties (`script_code`) and reloads it, ensuring the model is pre-configured with a floating health dial when pulled from the bag.
*   **Floating Health Tracker (`Floating_Health_Tracker.lua`)**:
    *   An embedded script that renders an XML health dial directly above or on custom components.
    *   **Custom Standee Behavior**: Places a high-hovering flat horizontal panel (`position="0 0 -300"`) directly over the standee's head, readable from any player angle.
    *   **Custom Double-Sided Tile Behavior**: Detects if a component is a map tile (`self.tag == "Tile"`). Places a flat horizontal tracker on the tile face (`position="0 0 -175"`). It queries `self.is_face_down` and hides the UI completely when flipped to its back face.
    *   **Class-Based Default Health**: Reads the card's `class` (Champion/Familiar/Minion/Talisman) straight out of the model's `GMNotes` ID (injected by the Model ID Injector) to decide the starting health value — Minions default to `2`, everything else defaults to `6`. This is independent of the Tile/Standee shape check above, since a card's class and its physical shape are separate concerns.
    *   **Performance Optimization**: Avoids heavy, frame-rate degrading `onUpdate()` loops. Rotation and visibility updates are triggered strictly on player-driven events (`onRotate` and `onDrop`). It waits for smooth movement to settle (`self.isSmoothMoving()`) before updating.
    *   **Secure Synchronized Logging**: Restricts modification. Any button click (`-` or `+`) broadcasts a synchronized, color-coded chat notification containing the player's name and the component's name to prevent stealth adjustments.
*   **Tile Controllers (`Deploy_Font_Tiles.lua` & `Deploy_Path_Tiles.lua`)**:
    *   Standalone map deployment buttons that automatically toggle between Recall and Deploy labels.
    *   Uses cached states on load, queries trigger zones, and implements error handling to ensure seamless physical board construction.
    *   **Shared grid origin**: both controllers and `TTS_Loader.lua`'s own `deployScenarioMap()` place tiles from the same top-left origin (`x = -10, y = 0.21, z = 10`) at `4.0` spacing, so a board built by either route lines up. Font tiles are the one exception — they stack *on top of* path tiles and so spawn at `y + 0.05` (`FONT_Y_OFFSET` in `Deploy_Font_Tiles.lua`). Keep these three copies in sync when changing the layout.
